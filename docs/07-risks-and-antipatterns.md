# 风险与反模式

## 主要风险

### 工程范围爆炸

独立开发者最容易同时尝试：

- 跨平台 UI
- DHT
- NAT 打洞
- 群组加密
- 音视频
- 频道
- 自动化
- 联邦

防范：一次只完成一条端到端链路，并为每个阶段设置验收门槛。

### 自研密码学

不要自行设计 Ratchet、群组密钥协议或底层原语。可以自定义消息事件协议，但密码学必须优先采用经过分析和维护的实现。

### PeerId 等同 UserId

网络节点身份不能替代长期用户身份，否则多设备、节点迁移和设备撤销都会失去清晰语义。

### 纯在线直连

没有 Mailbox 的 P2P 演示无法成为可靠聊天产品。

### Gossip 承担全部消息

Gossip 不自动提供离线持久化、精确收件确认和敏感关系保护。

### 把 TLS 当作端到端加密

TLS 只保护一段链路。Relay、Mailbox 或联邦节点之间转发的内容仍需应用层端到端加密。

### 所有消息全局排序

聊天消息只需要因果和局部顺序。强制全局共识会增加复杂度和网络分区时的不可用性。

### 机器人万能 Token

Agent 必须有独立身份和细粒度 Capability；高风险动作必须经过批准。

### 过早追求完全匿名

匿名网络、抗流量分析和开放发现会成倍增加反滥用难度。首版先做邀请制、端到端加密和最小元数据。

## 技术债警戒线

出现以下情况时应暂停增加功能：

- EventEnvelope 频繁破坏兼容性
- SQLite 投影无法从事件重建
- 重试造成重复消息
- 网络层类型渗透到 UI
- FFI 调用过于细粒度
- 节点角色写死在单个服务程序中
- 密钥与普通业务数据混存
- 没有协议测试向量
