# 核心威胁模型

## 1. 范围与安全声明

本文定义普通端到端加密聊天（`StandardE2ee`）的最低安全边界，适用于客户端、本地事件库、Direct、Relay、Mailbox、Directory/Bootstrap、Push Bridge、Blob 和备份恢复。它是实现与发布门槛，不是匿名网络覆盖层的替代品；后者另见 `future_plan/anonymous-network-overlay/`。

核心层承诺：未经授权的网络与服务节点不能读取消息正文或附件明文，接收端能验证发送设备与事件完整性，撤销与重放遵循明确语义。核心层不承诺隐藏通信双方的 IP、在线时间、通信频率或流量形状，也不能在端点已完全失陷后继续保护该端点可访问的数据。

本文中的“必须”是发布阻断条件。具体密码算法、密钥恢复方案和元数据最小化结果仍须独立设计、评审和测试；威胁已记录不等于这些功能已经实现。

## 2. 资产与安全属性

| 资产 | 必须保护的属性 |
|---|---|
| 用户根身份、设备授权链和恢复凭据 | 机密性（秘密部分）、真实性、不可回滚、可撤销性 |
| 设备私钥、会话状态、消息密钥和附件密钥 | 机密性、完整性、前向保密/失陷后恢复能力（由所选成熟协议提供） |
| 消息、附件、草稿、本地搜索索引和导出文件 | 机密性、完整性、按用户意图可用 |
| 不可变事件、父引用、发送者局部序列、控制 Epoch | 来源真实性、抗篡改、抗重放、确定性解释 |
| 通讯录、成员关系、Mailbox routing token、Push token | 最小披露、不可跨域关联、生命周期受限 |
| Relay/Mailbox/Blob 中的密文及投递回执 | 完整性、有限保留、配额隔离、不可被当作可信明文 |
| 本地数据库和加密备份 | 完整性、机密性、可恢复性、抗回滚 |
| 协议版本、算法套件和配置 | 防降级、来源可信、可审计变更 |
| 可用性资源 | CPU、内存、磁盘、带宽、连接数和任务队列保持有界 |

## 3. 信任边界

```text
用户
  │ 明确授权、验证联系人/新设备、保管恢复材料
  ▼
受信任客户端进程 ── OS keystore / 文件系统 / 通知 API
  │                       （平台是独立信任边界）
  ├── 本地 Event Store、投影、队列、密钥句柄
  │
  └── 不可信网络
       ├── 联系人的客户端（仅信任其有效设备证明，不信任其输入）
       ├── Direct / Relay / Mailbox
       ├── Directory / Bootstrap
       ├── Push provider
       └── Blob service
```

- 客户端密码边界以内可以接触解密后的用户数据；UI、插件、日志和崩溃报告不能因此获得默认访问权。
- 联系人拥有其收到的明文，可以截图、复制、举报或转发；联系人不是可信基础设施。
- 所有网络输入均不可信。TLS 只保护一段链路，不能替代应用层端到端加密、签名和边界检查。
- Relay、Mailbox、Directory、Push、Blob 及其运营者均按“可能恶意且可能串谋”处理；它们的可用性与返回值不是密码学信任根。
- OS、硬件 keystore 和依赖库属于供应链/平台边界。完整端点控制落入 A7，核心协议无法继续保护该端点上的可见数据。

## 4. 对手模型

对手可并用多种能力；除特别说明外，可观察、丢弃、延迟、复制、重放、乱序、篡改和伪造其控制边界内的数据。

| ID | 对手与能力 | 主要风险 | 核心缓解与剩余风险 |
|---|---|---|---|
| A0 | 本地旁观者，可看到锁屏、导出文件或未加密磁盘 | 正文、联系人和通知泄漏 | 安全存储、通知脱敏、加密备份、自动锁定；已解锁会话和用户主动导出仍可能泄漏 |
| A1 | 主动网络对手，可监听、阻断、重放、降级和劫持连接 | 内容泄漏、版本降级、流量分析、拒绝服务 | E2EE、签名、域分离、版本绑定、重放防护；IP、时序、尺寸和可用性不完全受保护 |
| A2 | 恶意联系人，拥有合法端点并可构造协议输入 | 骚扰、内容外传、畸形事件、回执/在线状态探测 | 授权与输入校验、封禁/静音、配额、最少回执；无法阻止接收者保存或公开合法收到的内容 |
| A3 | 恶意或失陷的 Relay/Mailbox，可串谋 | 丢弃/关联/重放密文、伪造回执、存储耗尽 | 不持有明文密钥、opaque envelope、签名/AEAD、幂等去重、回执分级、TTL/配额；仍能观察局部路由和时序并拒绝服务 |
| A4 | 恶意 Directory/Bootstrap 或 Sybil 节点集群 | 节点视图污染、Eclipse、定向到恶意服务、回滚 descriptor | 签名 descriptor、新鲜度/序列、来源和运营者多样性、自定义静态节点、equivocation 隔离；首次引导和大规模 Sybil 仍是可用性风险 |
| A5 | Push provider 或恶意 Push Bridge | token 关联、唤醒时序泄漏、伪造唤醒、通知内容泄漏 | Push 仅传随机/不可解释 WakeHint，不传消息/联系人/会话；客户端经认证通道拉取；平台仍知道应用安装和唤醒时间 |
| A6 | 恶意 Blob service | 附件替换、删除、尺寸/访问模式关联、存储炸弹 | 客户端流式加密，密文内容寻址，manifest/chunk/AEAD 校验，预算和配额；密文总量、分块和访问时间仍可见 |
| A7 | 失陷设备或恶意本地软件，能读取进程、UI、密钥或输入 | 冒充用户、读取历史与新消息、窃取恢复材料 | 撤销、密钥轮换、安全存储、最小密钥暴露和审计可限制未来影响；在检测和撤销前无法保证该设备上的机密性或真实性 |
| A8 | 供应链/更新对手，控制依赖、构建或发布渠道 | 后门、密钥窃取、协议偏离 | 锁定依赖、可复现/可验证构建、签名更新、SBOM、依赖审计和发布隔离；需运营流程持续保证 |
| A9 | 资源耗尽对手，拥有少量或大量身份/节点 | CPU、内存、磁盘、带宽、任务队列耗尽 | 解析前大小限制、分层配额、速率限制、并发预算、TTL、背压和可取消工作；不承诺在大规模阻断或资源饱和时持续可用 |

## 5. 组件级要求

### 5.1 设备、联系人与会话

- 根身份秘密、设备私钥、会话状态和恢复秘密不得以明文进入数据库、日志、指标、崩溃报告、剪贴板或网络 DTO。
- 私钥使用不透明句柄；密钥材料只在最小作用域暴露，缓冲区不允许 `Debug`/序列化并在释放时清零。
- 邀请必须有短有效期、单次使用和带外验证选项。联系人显示名或扫描二维码本身不是长期密钥真实性证明。
- 每个入站事件必须先做大小/版本/结构预算，再验证签名、设备授权状态、会话/控制 Epoch、AEAD、重放和依赖，验证完成前不得进入可见投影。
- 设备撤销不改写撤销前已按当时授权状态验证的历史，但该设备在撤销序列之后生成的事件和新会话建立必须拒绝。撤销传播期间 UI 不得把未知状态伪装成已验证。
- 恶意联系人输入永远不得触发任意文件写入、路径穿越、未授权能力调用或无界资源分配。

### 5.2 Relay 与 Mailbox

- 服务端只接收 opaque envelope、有限路由 token、到期时间和最少反滥用证明；schema 和日志不得出现 UserId、ConversationId、联系人、消息类型或正文。
- 持久化回执只证明某服务接受了密文，不证明目标设备收到、验证、解密或阅读；UI 和重试状态必须区分这些层级。
- 客户端必须容忍至少一次投递、重复、乱序、过期和伪造回执，以 `EventId`/envelope ID 幂等去重并只将有效事件提交本地一次。
- 每 token、来源、目标租约和全局资源均须有尺寸、TTL、速率、连接、存储和并发上限。认证失败不得泄漏收件箱是否存在。
- 单一 Relay/Mailbox 不得成为身份、密钥或历史的唯一信任/恢复来源；更换服务不能改变会话密码语义。

### 5.3 Directory、Bootstrap 与节点选择

- NodeDescriptor 必须签名并绑定版本、NodeId、能力、endpoint、sequence 和有效期；回滚、过期和同 sequence 多内容必须拒绝或隔离。
- 节点信誉只用于路由选择，不得替代用户/设备身份验证。自声明角色也不是可用性证明。
- 默认引导服务失效时必须允许显式静态配置；候选选择应避免单来源、单运营者或单网络前缀垄断。
- 发现查询不得包含 ConversationId、联系人或消息类型。缓存和 probe 必须有界，防止 descriptor/Sybil 洪泛。

### 5.4 Push

- Push payload 只能表示不可解释、短期、可重放安全的唤醒提示，不得携带正文、发送者、会话、消息类型、Mailbox routing token 或可跨会话稳定关联的标识。
- Push 不是送达证据或事实源；客户端被唤醒后必须通过正常认证、拉取、验证和去重流程取得事件。
- Push token 仅发送给所选 Push Bridge，静态加密存储，支持轮换和删除，禁止写日志或与用户公开身份一同暴露。

### 5.5 Blob 与附件

- 文件名、MIME、原始尺寸和附件密钥放入加密 manifest；服务只获得传输所需的密文长度与块标识。
- 明文导出前必须验证 manifest hash、chunk hash、AEAD tag、索引和总长度；部分成功不得产生被标记为完整的明文文件。
- 导入、解密、预览和导出均使用受控句柄与流式 I/O，限制声明长度、压缩比、块数、内存和并发；远端输入不得成为本地路径。
- 附件内容由联系人发送时仍可能恶意；调用平台预览器或外部应用必须经过用户动作和类型安全策略。

### 5.6 本地数据、备份与密钥恢复

- Mailbox、Relay、Blob 缓存和同步副本不是备份。备份必须认证加密、版本化、可完整验证，并在隔离 staging 中恢复后原子切换。
- 恢复秘密不得由服务节点单独持有或推导。丢失恢复材料时，系统不得通过降低身份验证强度“找回”身份。
- 恢复必须抵抗离线猜测（采用经评审 KDF/硬件密钥/多份凭据策略）、备份回滚、已撤销设备克隆和错误身份合并；失败响应不应成为凭据 oracle。
- 恢复到新设备默认产生新 `DeviceId` 并完成授权；恢复历史事实不自动恢复被撤销设备的权限。
- 具体恢复因子、阈值、KDF 参数、轮换、遗失和紧急撤销流程必须另立设计并通过测试。在此之前不得宣传“可恢复账户”，`TODO.md` 中“密钥恢复设计”保持未完成。

## 6. 元数据暴露与最小化

`StandardE2ee` 保护内容，不等于匿名。根据所用路径，不同实体仍可能看到：

| 观察者 | 可能看到 | 不应看到 |
|---|---|---|
| 直连联系人/网络 | 双方 IP、连接时间、字节量 | 未发送给该联系人的其他会话 |
| Relay | 相邻连接、时间、尺寸、临时路由信息 | 正文、附件密钥、房间名称和成员列表 |
| Mailbox | routing token、存取时间、密文尺寸、TTL | UserId、ConversationId、消息类型和正文 |
| Directory/Bootstrap | 查询方 IP、节点角色/endpoint 查询 | 联系人、会话和消息类型 |
| Push provider/Bridge | 设备/平台 token、唤醒时间 | 正文、发送者、会话和 Mailbox token |
| Blob service | 密文块、长度、上传/下载时间 | 文件名、MIME、明文和附件密钥 |

最低原则：不收集不是协议必需的字段；不把长期身份用于路由；按会话/用途隔离短期 token；批量或延迟不紧急回执；日志使用局部、短期关联 ID；明确 TTL 并可删除。每次发布必须运行数据流审计，列出每个服务实际收到、持久化和记录的字段。需要隐藏 IP、关系或流量形状时，必须启用单独评审的匿名覆盖层，不能扩大 E2EE 宣传口径。

## 7. 拒绝服务与滥用

本项目不承诺在全网封锁、DDoS 或所有候选节点被控制时保持可用，但必须确保攻击失败是有界、可恢复状态，而不是密钥泄漏、数据库损坏或永久队列阻塞：

- 所有 wire 对象在分配/解压/验签前检查编码深度、字段数和字节上限；未知版本 fail closed。
- 验签、KDF、解压、附件和 probe 等昂贵任务设每来源及全局并发预算，支持取消和背压。
- Relay/Mailbox/Blob 使用认证或成本证明、分层配额、TTL、速率限制与公平调度；不得靠可枚举用户 ID 返回差异化错误。
- 重试采用上限、指数退避和抖动；永久错误不无限重试；多路径不得形成放大环。
- 投影、Event Store、outbox 和 delivery queue 在重复/乱序/崩溃下保持幂等，隔离无效输入并允许用户清理。
- 封禁和举报是本地/运营策略，不能通过读取 E2EE 正文实现服务端默认扫描；任何可选举报须由用户明确提交选定内容。

## 8. 安全不变量

以下不变量适用于所有实现和传输适配器：

1. Relay、Mailbox、Directory、Push 和 Blob 的组合不持有解密聊天正文或附件所需的密钥。
2. 未通过签名、授权状态、会话策略、AEAD、重放和边界验证的输入不会进入可信 Event Store/可见投影。
3. 设备撤销不伪造历史，但阻止撤销点之后的设备权限；恢复不会复活已撤销设备。
4. 版本、算法、事件关联数据和签名 domain 被认证绑定；不允许静默降级、未知算法回退或“验签失败后继续”。
5. 网络投递按至少一次设计；重复/乱序不会导致本地事件多次提交、权限重复执行或明文重复导出。
6. 服务回执不冒充终端接收/验证/阅读证据，网络节点也不成为身份或消息事实源。
7. 私钥、会话状态、恢复秘密、Push token、明文和本地路径不进入日志、指标、崩溃报告或远程 DTO。
8. 所有不可信输入和后台任务都有尺寸、时间、并发、存储和重试预算；耗尽不会绕过验证或破坏已提交事实。
9. 备份和恢复 fail closed，损坏、回滚或错误凭据不会覆盖当前可启动 profile。
10. 默认服务全部不可用或被替换时，身份与已保存历史仍归用户；使用自定义节点不要求新身份或降级加密。

## 9. 明确非目标

- 在设备被完全控制、屏幕被观察或联系人收到明文后继续保证该明文机密。
- 在普通 Direct/Relay/Mailbox 模式下隐藏 IP、在线状态、通信关系、消息时间、方向和尺寸。
- 抵抗全球被动流量观察、广泛串谋或互联网级阻断；这些属于匿名覆盖层和网络可用性研究。
- 保证消息必达、服务永不丢失数据，或在合法接收者处实现不可复制/不可截图/可靠删除。
- 通过自研密码原语、区块链或全局共识解决端点安全、身份验证或滥用问题。
- 在没有独立设计和恢复材料的情况下保证账户或历史一定可恢复。
- 把 E2EE 宣传为恶意内容检测、垃圾信息治理或端点反恶意软件方案。

## 10. 验证与发布门槛

### 协议冻结前

- [ ] 为每个 wire 对象给出规范编码、签名/AEAD 关联数据、domain separation、版本和大小上限。
- [ ] 选择维护且经过公开分析的单聊加密实现，并记录算法、依赖版本、密钥删除和升级策略；禁止自研原语。
- [ ] 为身份授权/撤销、设备更换、会话建立、密钥 Epoch、回执分级和错误语义建立状态机。
- [ ] 完成数据流图：逐字段记录客户端、Relay、Mailbox、Directory、Push 和 Blob 可见/持久化/日志数据。

### 实现合入前

- [ ] 正向与负向测试向量覆盖篡改、错误签名/密钥、重放、乱序、降级、过期、撤销和跨 domain/cross-conversation 替换。
- [ ] 属性/模糊测试证明解析和投影在任意输入下无 panic、无界分配或验证绕过；所有限额有边界测试。
- [ ] 崩溃点测试证明 Event Store、outbox、队列、附件和恢复 staging 原子且可重建。
- [ ] 密钥/明文/路径/token 的日志与崩溃报告泄漏扫描通过；生产构建禁止危险调试输出。
- [ ] Direct、Relay、Mailbox、Blob 的多实现 conformance suite 通过相同安全语义。

### MVP 发布前

- [ ] A0–A9 攻击用例形成可复现安全测试；至少包含恶意联系人、失陷设备撤销、恶意服务串谋、Sybil/Eclipse、Push/Blob 泄漏和资源洪泛。
- [ ] 元数据最小化评审和恢复设计分别完成，未完成能力从 UI、README 和发布声明移除。
- [ ] 依赖审计、许可证/SBOM、签名发布和更新回滚保护就绪；高危依赖无未接受例外。
- [ ] 由未参与实现者完成安全设计评审；密码/协议关键实现发布前进行独立专业审计或明确标记为实验性、不可用于高风险场景。
- [ ] `SECURITY.md` 的私密报告路径已启用并实际演练，确认不会要求研究者公开零日细节。

### 每次发布

- [ ] 发布说明列出已验证的对手、仍可见元数据、已知限制、审计状态和安全相关变更。
- [ ] 回归测试向量、模糊测试语料、依赖审计、日志泄漏扫描和恢复演练全部通过。
- [ ] 新服务角色、字段、遥测、第三方 SDK 或权限均重新进行威胁建模；不满足安全不变量则阻断发布。

## 11. 维护

安全模型负责人在协议、安全边界、平台能力或服务数据流变化时更新本文；每个变化以 ADR 或 PR 说明新增资产、对手能力、元数据和验证用例。发现本文与实现不一致时，以更保守的用户安全行为为准：关闭未验证能力、避免静默降级，并在发布说明中披露差异。
